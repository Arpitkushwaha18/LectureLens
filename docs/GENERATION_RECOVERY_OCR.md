## Current retry lifecycle (supersedes the historical recovery policy below)

- Completed outputs are reused. Validated durable checkpoints are recovered without another provider request. **Retry** retains the file and selected outputs, reuses successful outputs, and generates only missing ones.
- Definitive rejection, invalid structured response, configuration/input failure and proven pre-dispatch cancellation release the active attempt. The next permitted student request gets a fresh token. Supabase creates a new job after terminal failure; SQLite records a new durable attempt on the existing operation row. Earlier errors, tokens, evidence and supersession decisions remain in private history. Stale workers cannot overwrite replacement attempts.
- Definitive student message: **“Generation failed. You can try again.”** Retry appears for safely repeatable outcomes. Authentication/model/input/configuration failures are not automatically replayed; Continue permits a new attempt after correction.
- HTTP 429 respects Retry-After. HTTP 500/502/503/504 and proven DNS/connection-refusal failures use exponential cooldown with jitter (60/120/240 seconds, capped at 300 seconds including jitter; longer Retry-After wins). The SDK performs one HTTP attempt. **No timer automatically spends another credit:** student Retry is required. A bounded three-attempt cycle can end terminally, but a definitive terminal failure is automatically superseded on the next safe student retry, not permanently locked behind an operator.
- Uncertain student message: **“We're checking your previous generation. We haven't started another request to avoid duplicate charges.”** **Check result** never dispatches Gemini or a caption request. It returns saved results, retains uncertainty, or enables Retry after definitive backend confirmation.
- Timeout, connection reset, unknown submission, stale dispatched leases without a definitive response, and uncheckable legacy paid outcomes remain fenced across model changes. Only informed operator resolution followed by explicit retry approval can release an uncheckable outcome. Waiting, restarting, changing models or checking the result cannot release it.
- Request identity includes source/content, output, language, model/settings and prompt/schema. The paid-operation fence intentionally excludes model/settings. File identity stays stable across parser versions. Legacy identities are recovered only by exact preserved-hash matching; a null identity no longer globally blocks unrelated work.

Its attempt count (2), token, expired deadline and unknown provider outcome remain preserved. It has no output/checkpoint and was **not abandoned or resent**. ## Operator-only procedure

Privately set a random 32+ character `OPERATOR_RECOVERY_TOKEN` in backend configuration, never any `VITE_` variable. Recovery is disabled without it. Send it as the Bearer authorization header to:

- `GET /api/v1/operator/jobs` or `GET /api/v1/operator/jobs/:id` for SQLite diagnostics, revision and audited events.
- Add `?store=supabase` for protected hosted diagnostics. Hosted mutation requires **migration 006**, local-only pending approval; a missing RPC fails closed.
- `POST /api/v1/operator/jobs/:id/recover` with `{revision, action, reason}`. The reason must be 20–1,000 characters. Use the revision from a fresh inspection; concurrent changes return conflict.

Actions:

| Action              | Required evidence/authorization                                             |
| ------------------- | --------------------------------------------------------------------------- |
| `recover_output`    | Validated persisted output/checkpoint; reuses it without another generation |
| `confirm_rejected`  | Recorded definitive HTTP rejection for the current attempt                  |
| `confirm_not_sent`  | Recorded absence of dispatch for the current attempt                        |
| `resolve_abandoned` | Explicit `acknowledgePossibleCharge:true` and informed operator reason      |
| `approve_retry`     | Earlier outcome explicitly resolved; three-attempt limit not exhausted      |

For this legacy row only `resolve_abandoned` is supported by available evidence; it is an **informed operator decision**, not a declaration that generation/billing never occurred. Active leases cannot be abandoned. Validated output must be recovered instead of retried. Every resolution preserves the original token/state in a private audit event, revokes the worker token, and prevents stale completion/failure from overwriting it. Future attempts durably record dispatch before HTTP, actual response status/request ID (including Gemini response ID), classification and validated output checkpoints. SQLite dispatch/evidence/checkpoint updates are atomic with their audit records. Student calls with absent/wrong credentials get 403 and cannot inspect jobs or recover them. Diagnostics are backend-only, no-store and exclude source text and secrets.

The student fenced message is:

> Your previous generation is still being checked. We haven't started another request, to avoid duplicate charges. Please try again after the previous job has been resolved.

Frontend does not offer transport-error retries or allow Continue after a non-retryable fenced failure. Local-only migrations 005 and 006 are tested in disposable PostgreSQL; **neither was applied to production**. Hosted new paid calls fail closed when migration-006 evidence recording is unavailable. Hosted deployment also needs 005's atomic cross-model claim fences; approval is required before enabling production generation. Hosted diagnostics currently show persisted fields; the private hosted audit table is not exposed through the HTTP inspection endpoint.

## OCR implementation and limits

PDFJS preserves order, page boundaries and text lines. Pages without text, or with fewer than `OCR_MIN_TEXT_CHARACTERS` (default 80) non-whitespace characters **and raster-image operators**, are selected for OCR. Short text-only pages are not unnecessarily OCRed. Rendering defaults to `OCR_DPI=150`, capped at 1,900 px on the longer side. A document-scoped native **Tesseract 5** engine reuses English/Hindi language data through Koffi in an isolated subprocess. Page rotation is corrected first, with bounded alternate orientations for low-confidence images. Identical rendered images reuse recognized text. Pages are sequential, so only one render/recognition is in flight per document; OCR engines are not shared between users.

Failures return `partial`, `retryable`, `failedPages` and/or `failedImages`, keeping successful pages, cells and sheet/image anchors. A partial extraction **does not call Gemini** until the user explicitly chooses “Use successfully extracted content.” Retry reprocesses only failed PDF pages or missing XLSX images, preserving successful extraction. Entirely unreadable PDFs cannot generate from failure markers. Parser-v3 extraction caches are separate; legacy extraction/material records remain intact. Cancellation is offered only during validation/extraction and kills parser/native OCR children; disconnection does not unlock an already-dispatched paid job. Progress reports actual reading, embedded-text extraction, scan detection, OCR page/image X of Y and preparation, without fake percentages.

Prerequisites (free/local): `brew install tesseract` on macOS, or `apt install tesseract-ocr libtesseract5 fonts-noto-core` on Debian/Ubuntu, then `npm --prefix backend run ocr:setup`. The setup script downloads pinned tessdata_fast 4.1.0 packs into private `backend/.cache/tessdata`. `OCR_TESSERACT_PATH` is retained for compatibility; the reusable engine now loads a shared library, auto-detected on macOS/Linux or set with `OCR_TESSERACT_LIBRARY`. Windows discovery is not verified.

Initialization is bounded to 10 seconds, each page to `OCR_PAGE_TIMEOUT_MS=15000` and the document to `DOCUMENT_EXTRACT_TIMEOUT_MS=180000`. Page timeout kills the engine; subsequent pages may start a fresh one. PDF checkpoints retain completed pages at the document deadline; remaining pages are retryable. **XLSX document-deadline recovery is not checkpointed yet** (individual image failures preserve cells). OCR image budgets default to 30 and max at 50; remaining pages/images are reported rather than destroying successful extraction.

Preserved limits: **20 MiB/file, 100,000 source characters / 400,000 UTF-8 bytes, six outputs**, existing workbook/ZIP limits, streaming, handwritten-style notebooks, PDF export and exact Notes Gallery fallback. Complex tables/formulas, handwriting, arbitrary low-quality scans and image regions inside otherwise text-rich pages are not guaranteed accurate. XLS embedded images remain unsupported; XLS cells/CSV are unchanged. Native raster memory requires deployment-level resource limits in addition to worker V8 limits.

## Measured before/after

Same generated fixtures, local macOS, Node v24.16.0, provisioned eng+hin data, no Gemini. These are controlled **synthetic** multi-page documents, not benchmarks of unavailable original large uploads. Single runs are not latency guarantees.

| Fixture                                                |   Before |    After | After coverage                                 |
| ------------------------------------------------------ | -------: | -------: | ---------------------------------------------- |
| 12-page mixed text/scans, English/Hindi and rotation   | 2,104 ms |   888 ms | 6 scanned + 6 embedded-text pages; no failures |
| 8-page scanned English/Hindi/rotation PDF              | 2,565 ms | 1,097 ms | All 8 scanned pages; no failures               |
| XLSX, two identical anchored images on separate sheets |   323 ms |   226 ms | Both associations, one recognition             |

Before combined native-process recognition/initialization took 1,403 / 1,720 / 197 ms across 9 / 11 / 2 spawned orientation attempts. After recognition took 364 / 484 / 44 ms across 6 / 8 / 1 attempts; each document loaded one engine. Library binding was about 3 ms and language loading 33–34 ms per document. Baseline process startup/language loading cannot be separated from CLI recognition retrospectively; they were recorded as combined `ocr-engine` time. PDF render sums: before 43 / 54 ms, after 43 / 56 ms. Preprocessing: before 120 / 158 / 17 ms, after 60 / 78 / 8 ms. XLSX relationship/image extraction stayed around 7 ms.

Sampled main-process RSS maxima were 439/449/459 MiB before and 375/383/389 MiB after, but these are **not total OS peak memory**: worker RSS covers the host process, while OCR children report their own RSS separately. The old CLI child was not sampled, so no total-memory reduction is claimed. Subprocess lifecycle tests verify zero tracked OCR processes after repeated sessions and timeout; cancellation tests verify parser rejection and termination. Native allocations are not bounded by V8 heap limits.

Raw evidence: `backend/.cache/verification/ocr-before.json`, `ocr-after.json`, generated by `backend/scripts/ocr-profile.mjs` after a backend build. After artifacts include failed-page counts so fast failures are not mistaken for speedups.
